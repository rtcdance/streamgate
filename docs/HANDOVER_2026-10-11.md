### 9.4 Go 1.26 暴露的一个既有生产缺陷(已修)

`pkg/monitoring/alerts.go:152` 用 `time.Now().UnixNano()` 生成 alert ID。**Go 1.26 下 darwin 连续调用会返回相同值**,导致同一瞬间触发的两条规则 ID 碰撞 —— `am.alerts[alert.ID] = alert` **静默覆盖第一条**。

- **A/B 证据(同机器,同代码,仅换工具链)**:
  - Go **1.25.0** @ `e13f31d`,`-count=100` × 3 轮 → **全绿(300 次零失败)**
  - Go **1.26.9** @ 同代码,`-count=100` × 3 轮 → **3 个测试间歇失败**(`GetActiveAlerts` / `GetAlertCount` / `GetAlertsByLevel`)
- **修复**:`seq atomic.Uint64` 后缀 → 修复后 Go 1.26.9 下 `-count=100` × 3 轮**全绿**
- 结论:这是**既有的生产缺陷**,只是被 Go 1.25 的时钟粒度掩盖;不是测试问题。

1. 该豁免从未生效 —— 门禁实际上**一直在拦截「不可修复」的 CRITICAL/HIGH**,比设计意图更严格;
2. 也正因如此,之前报告的 6 个 HIGH 全都是 `fixed` 状态(能被拦截),这与实际观察一致;
3. 本次把死配置**删除**而非改写成 `ignore-unfixed: true` —— 保留更严格的行为,避免降级门禁。若将来基础镜像出现上游未修复的 HIGH,应在**该处加文档化例外**,而不是整体放宽。

**同时纠正**:`§4.3` 里那句"Trivy 应只剩 `--ignore-unfixed` 覆盖的项"是错的 —— 它从未生效。已在 `build.yml` 注释中写明这段历史。
